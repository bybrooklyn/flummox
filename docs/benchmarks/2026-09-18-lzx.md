# Flummox and WOF/LZX corpus comparison

This run compares Flummox's version 2 store with a strong WOF/LZX proxy over
the same complete file corpus. It is an engineering benchmark, not a marketing
claim about every game or Microsoft's encoder.

## Result

| Game | Logical bytes | Flummox allocated | Flummox retained | WOF/LZX proxy allocated | WOF retained | Flummox difference |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Balatro | 66,662,933 | 60,248,064 | 90.38% | 60,219,392 | 90.33% | -28,672 bytes |
| Bridge Constructor Portal | 246,114,518 | 103,780,352 | 42.17% | 106,717,184 | 43.36% | +2,936,832 bytes |
| Half-Life | 667,402,434 | 327,618,560 | 49.09% | 327,430,144 | 49.06% | -188,416 bytes |
| Terraria | 831,366,992 | 639,823,872 | 76.96% | 692,367,360 | 83.28% | +52,543,488 bytes |
| **Total** | **1,811,546,877** | **1,131,470,848** | **62.46%** | **1,186,734,080** | **65.51%** | **+55,263,232 bytes** |

A positive difference means Flummox used less space. Across these four
installed games, Flummox retained 3.05 percentage points less data and saved
55.3 MB more than the proxy. Balatro and Half-Life were ties within 0.05
percentage points. The larger wins came from Bridge Constructor Portal and
Terraria.

The [raw JSON](2026-09-18-lzx.json) contains the corpus fingerprints, chunk
counts, metadata sizes, and timings used for this table.

This table measures a single store per game. Version 3 pool sharing can reduce
Flummox's marginal allocation further when games or retained versions contain
matching chunks. The WOF column has no cross-game sharing.

## Cross-game pool result

Two related game pairs were then written as version 3 stores in one shared
pool. The independent column sums each store's allocated blocks as if its chunk
objects had separate inodes. The pooled column counts each inode once across
both stores and the pool.

| --- | ---: | ---: | ---: | ---: | ---: |
| Substrate demo and full game | 404,929,005 | 210,247,680 | 121,470,976 | 88,776,704 | 42.22% |
| Slay the Spire and Downfall | 1,551,959,842 | 1,331,015,680 | 1,192,247,296 | 138,768,384 | 10.43% |

The Substrate pair retained 30.00% of its logical size after compression and
sharing. The same version 3 stores retained 51.92% when counted independently.
Across both pairs, pooling saved another 227.5 MB after compression. The
[pool JSON](2026-09-18-pools.json) includes each store summary and allocated
block count.

## Method

Flummox ran `pack benchmark GAME --maximum`, which compares zstd levels 9 and
15 for each unique content-defined chunk, keeps the smaller encoding, verifies
the completed store, and includes its header and index. The table rounds each
store to one 4 KiB allocation unit.

The proxy used wimlib commit `cd5e231c348c255ae5088873b5a66ee0eb96fa07`
at LZX level 50. Each file was divided into independent 32 KiB chunks, matching
Microsoft's documented WOF/LZX access unit. Every compressed chunk was decoded
and compared with its input. The result includes WOF's per-file chunk-offset
table and rounds each file to 4 KiB. A file remained raw whenever its estimated
WOF allocation was not smaller, which favors the proxy.

The benchmark generated a SHA-256 corpus fingerprint from each relative path,
file size, and file payload. Source counts from the Flummox build and the LZX
walk had to match before a result was emitted. The games were locally installed
Steam versions measured on Linux 7.2.3 with an AMD Ryzen 7 9700X and Rust
1.98.1. The source folders were read only.

## Reproduction

Build the helper against wimlib:

```sh
cc -O2 -Wall -Wextra -Werror \
  $(pkg-config --cflags wimlib) tools/wof-lzx-helper.c \
  $(pkg-config --libs wimlib) -o /tmp/wof-lzx-helper
```

Run both encoders over one source tree:

```sh
flummox --json pack benchmark /path/to/game --maximum \
  --wof-lzx-helper /tmp/wof-lzx-helper
```

On Windows 10 or 11, the exact WOF path uses `compact.exe` on a disposable
copy and measures allocation through `GetCompressedFileSizeW`:

```powershell
.\tools\measure-wof-lzx.ps1 -Source 'D:\Games\Game' -Scratch 'D:\Scratch'
```

Compare only records whose `corpus_sha256`, file count, and logical byte count
match. The Windows result is the required value for a direct Game Compressor
claim because Game Compressor uses Windows' native LZX implementation.

Microsoft documents WOF/LZX as 32 KiB chunks in
[`WOF_FILE_COMPRESSION_INFO_V1`](https://learn.microsoft.com/en-us/windows/win32/api/wofapi/ns-wofapi-wof_file_compression_info_v1).
The current Game Compressor feature set and LZX backend are described on its
official [Steam page](https://store.steampowered.com/app/4339880/Game_Compressor/).
The proxy encoder comes from [wimlib](https://github.com/ebiggers/wimlib).
